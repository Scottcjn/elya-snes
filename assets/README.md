# Assets

## logo — Elyan Labs startup screen

`logo_source.png` (1536x1024) converted by `tools/png2snes.py` at 4 colours.

| | |
|---|---|
| unique tiles | **109** of 896 slots |
| CHR | 3.4 KB (4bpp planar) |
| tilemap | 1.8 KB (with H/V flip bits) |
| palette | 4 entries of 15, index 0 transparent |
| **VRAM** | **5.2 KB of 64 KB** |

`logo_preview3x.png` is exactly what the PPU renders, at 3x for inspection.

**The palette row is an argument.** `png2snes.py ... 4 ramp 2` puts `2` in every
tilemap word's palette field, and the ROM loads `logo.pal` to CGRAM 32, which
is palette 2. Before that argument existed the tool emitted no palette field at
all, so the map selected palette 0 while the colours were loaded at 32 — and
the logo drew in the *text* palette, black and white, with both assets
perfectly correct. See FINDINGS entry 9.

### Why 4 colours and not 15

A frequency-based quantiser is the wrong tool for a two-tone logo. Red covers
most of the frame, so median-cut spent **every** palette entry on shades of red
and the white lettering disappeared — 704 unique tiles and an illegible result
that was, in colour-error terms, optimal.

`png2snes.py` instead takes the darkest and lightest colours actually present,
builds an explicit ramp between them, and assigns by luminance. 704 -> 109 tiles.

The source red is not flat (11,610 unique colours), so every *extra* palette
entry fragments the background into hundreds of near-identical tiles. Four is
the point where the curves are smooth and the flats still deduplicate.

## The game's art

Everything below is generated by a tool in `tools/`, from a source that is
either a hand-authored grid in that tool or an SDXL + trained-LoRA render in
`sprites/`. Nothing is a binary somebody dropped in.

| file | from | what it is |
|---|---|---|
| `font.chr` | `tools/mkfont.py` | 96 glyphs x 2 pages + 4 box tiles, 2bpp, 3,136 B |
| `obj.chr` `.pal` `.inc` | `tools/mkart.py` | the whole object sheet, 160 tiles, 5,120 B |
| `bg1.chr` `.pal` | `tools/mkbg.py` | level tiles, 5 tiles, 160 B |
| `bg2.chr` `.pal` | `tools/mkbg.py` | clouds, 15 tiles, 480 B |
| `bg3.pal` | `tools/mkbg.py` | three text palettes: sky, box, question |
| `level.map` `.solid` | `tools/mkbg.py` | 64x32 tilemap and its collision array |
| `clouds.map` | `tools/mkbg.py` | 32x32, wraps by itself at 256 px |
| `sky.hdma` | `tools/mkbg.py` | 28 bands of 8 scanlines, 141 B |

`level.solid` exists so the physics reads solidity out of a byte array rather
than by decoding tilemap words: the level and its collision come out of the
same array in the same pass and cannot drift apart.

### Why the object sheet is 128 pixels wide

Not a packing choice. OAM addresses a 32x32 object by the top-left tile of a
4x4 block in a **16-tile-wide** CHR grid, so sprites sit on that grid rather
than being packed tightly.

### Elya is pixelised here, not by the generator

The renders in `sprites/` are ~1024 px paintings *of* pixel art. `mkart.py`
crops to content, downscales the coverage mask separately from the premultiplied
colour, and snaps to one fifteen-colour object palette.

Two things that had to be learned by looking at the result:

* **Test for background before the downscale, not after.** The first version
  box-filtered first, so every edge pixel had already been averaged with the
  paper, and the light grey that produced snapped to the apron white — Elya came
  out wearing a halo.
* **Scale by height, not by bounding box.** Her running pose has a skirt sweep,
  so fitting the whole box inside a 32x32 cell made a 32-pixel-tall character 18
  pixels tall.

### The three objects that are drawn by hand

The `@` block, the coin and the nabla are authored at native size in
`tools/mkart.py`, because a 16x16 object has 256 pixels and a downscale of a
512 px render spends most of them on mush — which is what `docs/ART_SPEC.md`
says in as many words.

`sprites/at_block.png` is **not used**: it is a 3D render of a `?` block, and
the brief requires an original `@`. The `@` glyph that ships is ellipse
geometry rather than freehand, because three hand-drawn attempts at 10 to 14
pixels came out as a black blob or a spiral; the shape is the CP437 idiom, a
ring with a `c` inside, which is what still reads as `@` at twelve pixels.
`sprites/nabla.png` is not used either — it is a red demon rather than a
downward triangle, and a `∇` at 16 px is a better drawing than a 512 px
monster downscaled.
